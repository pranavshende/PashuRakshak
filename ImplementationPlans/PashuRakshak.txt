1. Product Requirements Document (PRD)
1.1 Product Overview
PashuRakshak is an offline-first Edge AI system that detects livestock diseases — Lumpy Skin Disease (LSD), Foot-and-Mouth Disease (FMD), and Mastitis — directly on a farmer's phone. It combines on-device CNN inference (MobileNetV2 / EfficientNetB0 via TensorFlow Lite) with a clinical symptom rule engine to produce a hybrid diagnosis, and works fully offline with opportunistic cloud sync.
1.2 Problem Statement
Rural farmers often lack immediate veterinary access and reliable internet connectivity. Delays in diagnosing LSD, FMD, and Mastitis drive up livestock mortality and economic loss. PashuRakshak brings diagnostic capability directly to the farmer's phone, working fully offline, and reconciles with the cloud opportunistically once connectivity is restored.
1.3 Goals & Objectives
Provide accurate, offline, on-device disease detection for livestock at the point of need.
Minimise time-to-diagnosis in low-connectivity rural regions.
Route farmers to the nearest available veterinarian using location-based search.
Give administrators visibility into regional disease trends via a web dashboard.
Keep the platform maintainable with a single unified codebase across mobile and web.

1.5 Core Product Requirements
Functional Requirements
Offline diagnosis using on-device TFLite inference — no internet required.
Symptom logging via tabular clinical inputs feeding a rule engine.
Hybrid inference engine blending 70% vision-model score with 30% symptom-based rule score.
Multilingual, icon-driven UI for users with low digital literacy.
Vet routing — nearest-vet lookup via PostGIS geo-proximity search.
Medicine recommendations from a cached reference dataset.
Cloud sync — bulk upload of cached predictions once connectivity returns.
Web admin dashboard for outbreak monitoring and vet management.
Regional outbreak push/realtime alerts.
Audit logging of admin data access.
Non-Functional Requirements
Availability: core diagnosis must work with zero connectivity.
Security: JWT/Supabase Auth plus Postgres Row-Level Security as defense in depth.
Scalability: comfortably support 10,000–50,000 users on the target infrastructure.
Performance: read-heavy geo queries must be cache-backed; sync bursts must not block the event loop.
Observability: crash and latency visibility via Sentry/APM.
Portability: one codebase serving iOS, Android, and Web.

2. System Design
2.1 Architecture Style
Edge-heavy client-server architecture with a managed backend-as-a-service core, plus a dedicated ML microservice for anything the edge model can't do.
Client: One Expo (React Native + Expo Router) app, compiled to iOS, Android, and Web. Farmer flows are mobile-first; the admin dashboard is a web-optimized route group in the same app.
Backend: Supabase — Postgres (with PostGIS), Auth, Storage, Realtime — fronted by a thin Node.js/Express layer for logic that doesn't belong in the database (hybrid inference blending, ML microservice orchestration, rate limiting).
ML: TFLite on-device for offline inference; a small FastAPI microservice for server-side fallback/heavier models.

2.3 Design Patterns Used
Offline-first sync: optimistic local writes, background reconciliation.
Hybrid inference: vision-model score (70%) blended with symptom-based rule score (30%).
Route-group-based platform splitting: Expo Router groups ((farmer), (admin)) instead of two separate apps.
Database-enforced authorization: Postgres RLS policies as a second layer under the API's own auth checks.

2.5 Authentication Flow
Option A — Supabase Auth (recommended, fits phone-first users)
Farmer requests OTP via supabase.auth.signInWithOtp({ phone }).
Supabase sends SMS OTP, verifies, returns a session JWT.
Client stores the Supabase session (SecureStore on native, encrypted storage on web).
Express API verifies the Supabase JWT on each request using Supabase's JWT secret.
RLS policies use auth.uid() directly — no separate user-id mapping needed.
Option B — Keep custom JWT (Passport), Supabase as pure Postgres
Same flow as v1 (bcrypt.compare → jsonwebtoken), but users table is managed by Prisma against Supabase Postgres.
RLS policies then need a custom claim (via a Postgres function reading a signed JWT claim) since auth.uid() won't be populated.
Option A removes an entire subsystem (Passport, bcrypt, custom token issuance) and is the lower-maintenance path — flagged as the default recommendation.
2.6 Hybrid AI Flow (Server-Side Fallback)
Image uploaded to Supabase Storage; the API receives the storage path (not the raw file).
API calls the FastAPI ML microservice over HTTP with the storage path.
ML service downloads the image, runs inference, returns confidence scores.
API applies the clinical rule engine (rulesEngineService.js).
Scores blended (70% vision / 30% symptoms) and written via Prisma Client.

2.9 PostGIS Query (Prisma Raw SQL)
Prisma Client has no query builder for geography types. The location column is declared Unsupported(...) so migrations can create it, but nearby-vet lookups must go through raw SQL. A GIST index on location is mandatory — without it this query becomes a full table scan.
const nearbyVets = await prisma.$queryRaw`
  SELECT id, name, phone,
    ST_Distance(location, ST_MakePoint(${lng}, ${lat})::geography) AS distance_m
  FROM "Vet"
  WHERE ST_DWithin(location, ST_MakePoint(${lng}, ${lat})::geography, 25000)
  ORDER BY distance_m
  LIMIT 10;
`;

2.10 Row-Level Security Policies
alter table "Prediction" enable row level security;
 
create policy "Users see only their own predictions"
on "Prediction" for select
using (auth.uid()::text = "userId");
 
create policy "Admins see everything"
on "Prediction" for select
using (exists (
  select 1 from "User" u where u.id = auth.uid()::text and u.role = 'ADMIN'
));

2.13 Security Review
Auth: Supabase Auth handles token issuance/rotation/revocation.
RLS: Postgres-level policies as a second layer under API checks.
Rate limiting: add express-rate-limit on /auth/* and /predict/analyze.
Command injection: eliminated by removing child_process.spawn in favor of an HTTP call to the FastAPI microservice.
Input validation: add Zod schemas on all API inputs.
Storage access: Supabase Storage buckets for prediction images should be private, served via signed URLs with short expiry.
2.14 Performance & Scalability Review
Connection pooling: Supabase's built-in PgBouncer — Prisma uses the pooled DATABASE_URL (port 6543) for runtime queries and directUrl (port 5432) for migrations.
PostGIS: a GIST index on Vet.location is mandatory; without it, ST_DWithin queries force full table scans.
ML inference: a standalone FastAPI microservice lets the API scale independently of inference load.
Caching: Redis in front of /vets/nearby and /medicines — these are either static or change infrequently.
2.15 Scaling Triggers
Signal
Action
Redis cache hit rate drops / Postgres CPU rises during sync bursts
Add a read replica for /vets/nearby and admin dashboard queries, keep writes on the primary
FastAPI ML service p95 latency climbs under load
Scale it horizontally (it's stateless) behind a load balancer
/predict/sync batches start timing out
Move sync processing to a queue (Postgres-backed job table or lightweight queue)
Supabase project approaches plan limits (connections, storage)
Evaluate a paid tier bump before anything architectural

2.16 Failure Modes & Graceful Degradation
Supabase unreachable: the app is offline-first by design — farmers keep diagnosing locally; sync queues until connectivity + Supabase are both back.
Partial sync failure (batch of 20, 3 fail): /predict/sync reports per-record success/failure, not all-or-nothing.
ML microservice down: /predict/analyze fails over to “on-device result stands as final” rather than blocking the farmer.
Redis down: reads fall through to Postgres directly (slower, not broken) — cache is an optimization layer, never a hard dependency.
